# grizzly-agent workspace — Implementation Phases

> Module level only. No file or line references — those get mapped in each phase's own session. Each phase is self-contained, depends only on phases before it, and is verifiable on its own. Read `design.md` in this directory first; every term used here is defined there.

Each phase lands as its own branch and PR in the repository it changes, and passes that repository's full local gate (`just ci-local` or its equivalent) before merge. Dependencies are pinned to the version verified current and maintained at the moment the phase adds them.

Phases 9–11 depend on earlier phases but not on each other beyond what is listed; phases 6 and 8 change sibling repositories and each pins grizzly-agent to a revision containing its preconditions.

## Phase 1 — Workspace foundation and current-state docs

- **Modules:** repository root (workspace manifest, shared lint table, toolchain, deny policy, `justfile`, git hooks, contributor guide, README, decision records, design archive); new `grizzly-agent` facade package; new `grizzly-agent-core` package.
- **Preconditions:** none.
- **Shape when done:**
  - The repository is a Cargo workspace. Every member inherits the workspace lint table unchanged; the strict lint set is exactly as strict as before.
  - `grizzly-agent-core` holds the existing conversation and error types with the three changes the design specifies: `TurnFailure` reduced to what is still a failure (its budget and stall variants removed — Phase 9 reshapes it into `RunFailure`), `ProviderFailure::InvalidRequest` added, `Content::Reasoning` carrying text plus an optional signature. `schemars` is gone from the dependency tree.
  - The `grizzly-agent` facade exists with the feature names from the design (`anthropic`, `openai`, `skills`, `eval`, `test-support`) declared, curated `#[doc(inline)]` re-exports of core's current public items, and a test referencing every re-exported item. Features whose crates do not exist yet are declared but empty.
  - `justfile` recipes and git hooks operate on the whole workspace. A recipe exists for the provider feature matrix (no provider feature, each alone, both), even though providers do not exist yet.
  - Documentation is current state: README rewritten around the workspace, the "would I use this again?" admission bar, the facade-plus-prompts consumption rule and the same-revision rule for git dependencies. New decision records supersede the admission-test/single-crate decision, the no-streaming decision, the schemars tool-schema decision, and the skills parsing/policy-scope decision; superseded records are marked as such and link their successors. The primitive survey moves to the archive. The contributor guide describes the workspace.
- **Verification:** the full gate passes across the workspace; `cargo tree` shows no `schemars`; a consumer-style test crate (or the facade's own test) uses `grizzly_agent::Message` etc. through the facade; the hooks reject a staged `#[allow(` in a member crate; the superseded records and new records exist and cross-link.

## Phase 2 — Core tool model

- **Modules:** `grizzly-agent-core` (tools).
- **Preconditions:** Phase 1.
- **Shape when done:** `ToolSpec` (name and description as `Cow<'static, str>`, parameters as a JSON value), the `ToolDefinition` trait with its associated `Params` type, `NoParams`, the object-safe `ToolHandler` trait (spec method; call method taking raw JSON arguments and `&ToolContext`), the typed adapter from a `ToolDefinition` plus an async function of `(Params, &ToolContext)` to a `ToolHandler`, `ToolContext` (a `tokio_util` `CancellationToken`, first-wins stop-request slot holding a reply and a reason), and `ToolSet` (ordered, keyed by wire name, duplicate names rejected at construction, advertises specs in order, dispatches by name with `ToolFailure::Unknown` listing registered names). All of it re-exported through the facade.
- **Verification:** unit tests cover: typed adapter parses valid arguments and converts invalid ones into `ToolFailure::InvalidArguments` text a model can act on; `NoParams` rejects unknown fields; a hand-written runtime tool with owned strings registers and dispatches; duplicate registration fails; unknown dispatch lists available names; two stop requests in one context keep the first; the facade exposes every new item.

## Phase 3 — Core model calls and streaming

- **Modules:** `grizzly-agent-core` (provider contract, requests and completions, accumulator, retry, `Model`, test support).
- **Preconditions:** Phase 1.
- **Shape when done:** the object-safe `Provider` trait returning a boxed `Send` stream of `CompletionEvent`s; the closed `CompletionEvent` enum (text delta, reasoning delta, tool-use start, tool-use arguments delta, usage, finished); `CompletionRequest` (messages, tool specs, optional max tokens and temperature, optional response format) with the design's request invariants enforced by `Model` as `ProviderFailure::InvalidRequest`; `Completion` (assistant message, all-optional usage, classified plus raw stop reason, reported model id); the public `CompletionAccumulator` with the block-ordering, argument-parsing and max-tokens truncation rules; the pure retry decision plus full-jitter combinator with the design's defaults and injectable sleep and jitter; `Model` with `complete` (buffered, whole-call retry) and `stream` (retry only before the first yielded event) and an optional whole-call timeout; the scripted provider behind `test-support`, including its exhaustion failure. Re-exported through the facade; the facade's `test-support` feature forwards to core's.
- **Verification:** unit tests driven by the scripted provider cover: event sequences reassembling into correctly ordered blocks; interleaved tool-call argument fragments; unparseable arguments as a decode failure, except under max-tokens where the incomplete block is dropped; a stream ending without `finished` failing retryably; `complete` retrying mid-stream failures; `stream` retrying a pre-first-event failure but not a post-first-event one; the default retry schedule under deterministic jitter, including `Retry-After` taking the larger value; non-retryable failures not retried; each request invariant rejected with a message naming it; the whole-call timeout; the scripted provider's exhaustion message. Core still has no HTTP dependency (`cargo tree`).

## Phase 4 — Providers

- **Modules:** new `grizzly-agent-providers` package (OpenAI-compatible provider, Anthropic provider, shared streaming-transport helpers); facade features `openai` and `anthropic` wired to it.
- **Preconditions:** Phase 3.
- **Shape when done:** both providers implement `Provider`, always stream on the wire, and meet every obligation in the design's Providers section: usage requested and surfaced, finish-signal requirement, 45-second default idle timeout (configurable), mid-stream error payloads and malformed chunks mapped to failures, fragmented tool calls translated to id-addressed events, arbitrary chunk boundaries handled, HTTP status and `Retry-After` classified into `ProviderFailure`. Wire translation in both directions is pure functions. The OpenAI-compatible provider takes a base URL and optional API key, flattens content per the design's mapping, reads reasoning under all three spellings, and maps the response format to strict `json_schema` output. The Anthropic provider lifts and joins head system messages, maps blocks natively, round-trips signed reasoning, drops unsigned reasoning, and maps the response format to Anthropic's native structured-output parameter (wire form verified against Anthropic's current API docs in this phase). Neither provider ignores a response format. HTTP is compiled only when a provider feature is on.
- **Verification:** unit tests feed recorded SSE bodies for each provider through the reader split at every byte boundary and assert the event sequence; tests cover each failure mapping, the mixed tool-result-plus-text user message, multiple head system messages, reasoning round-trip, and a stream without a finish signal; the provider feature-matrix recipe builds all four combinations; ignored-by-default live tests (enabled by environment variables naming an endpoint, key, and model) complete a simple prompt and a one-tool round trip against each real API, and are run once by hand before merge.

## Phase 5 — Prompts crate

- **Modules:** new `grizzly-agent-prompts` package (frontmatter default face, `codegen` feature, `verify` feature), ported from gameservers' `prompt-lib`.
- **Preconditions:** Phase 2.
- **Shape when done:** the default face splits Markdown into frontmatter and body and parses frontmatter with `yaml-rust2`, with no dependency on core. `codegen` loads and validates a prompt tree with fields hand-mapped from `yaml-rust2` — same file format, same validation rules, same file-naming error messages, parameter order preserved — and emits a module that references core types through the configurable crate path (default `grizzly_agent`), wraps `spec()` strings for `ToolSpec`'s `Cow` fields, and emits a `ToolDefinition` impl per tool bound to its inline, shared, or `NoParams` params type, while keeping every previously generated item. The one-argument build-script entry point still works, and a builder sets the crate path. `verify` behaves as before. `serde_yaml_ng` is not used anywhere in the workspace.
- **Verification:** every ported `prompt-lib` test passes against the new parser; the golden generated-module fixture is updated and compiles against core as a dev-dependency, including using a generated tool through `ToolSet` via the typed adapter; a test (or documented one-off check) runs `load` over a copy of gameservers' real prompt tree with no errors, and the emitted module differs from `prompt-lib`'s output only in crate paths, `Cow` wrapping, and the added `ToolDefinition` impls; `cargo tree` for a build-edge consumer of `codegen` does not include core.

## Phase 6 — gameservers onto grizzly-agent prompts

- **Modules:** grizzly-gameservers — bot crate's build script, dependency edges, tool-spec conversion into its wire type, annotation verification test; workspace membership; contributor guide and design docs.
- **Preconditions:** Phase 5 (and Phases 1–2 through it), on a grizzly-agent revision the bot pins.
- **Shape when done:** the bot depends on `grizzly-agent-prompts` (`codegen`) on its build edge, (`verify`) on its dev edge, and `grizzly-agent` on its normal edge; its prompt tree is unchanged; its conversion from `ToolSpec` to its own wire tool type works with `Cow` fields; its hand-written dispatch is unchanged. The in-repo `prompt-lib` crate is deleted and removed from the workspace. The contributor guide's prompt-library section points at the new crate, and the old prompt-lib design doc is archived.
- **Verification:** gameservers' full gate passes; the generated prompts module differs from before only as described in Phase 5; the annotation verification test passes against the real tree; `cargo tree` shows no `grizzly-prompt-lib` and no `serde_yaml_ng` pulled in by prompts; the bot's existing agent and tool tests pass unchanged.

## Phase 7 — Eval shared core and ResponseEval

- **Modules:** new `grizzly-agent-eval` package (case metadata, repeat verdicts and categories, check result, aggregation, report and summary rendering, per-invocation directory helper, suite result, ResponseEval trait and runner); facade feature `eval`.
- **Preconditions:** Phase 3.
- **Shape when done:** the shared core exactly as the design specifies, all public: case metadata with default two-thirds pass rate and canaries pinned at 1.0; the five verdict categories with `Unparseable` and `Unavailable` never merged; check result; per-case aggregation including per-category counts and latency and usage summaries; the schema-versioned JSON report with UUID v7 invocation id, consumer settings object and per-repeat consumer detail; the plain-text summary; the directory helper; the suite result. ResponseEval: the case trait (build request, parse, score, and an optional per-case timeout that defers to the runner's default, sets its own, or sets none) and a runner taking a `Model`, a default timeout, concurrency limit and cases, classifying provider failures and timeouts as `Unavailable` and parse failures as `Unparseable`, recording raw reply and usage, keeping the raw reply in the detail on a miss, and running repeats concurrently up to the limit.
- **Verification:** tests driven by the scripted provider produce each category deliberately (right answer, wrong answer, unparseable text, pre-stream failure, timeout) and assert classification and report contents; threshold and canary arithmetic is tested; concurrency never exceeds the limit (observed via the scripted provider); the report round-trips through JSON and renders the summary; the eval crate depends on core but not on providers (`cargo tree`).

## Phase 8 — gantry onto grizzly-agent providers and ResponseEval

- **Modules:** gantry — model client and chat types (removed), agent loop and context assembly, tools' advertised specs, watcher, policy judge, observer and reflector roles, events and transcript recording, structured-output requests, eval suite (role runner, scorer, report, invocation), configuration, tests and fakes, decision records and docs.
- **Preconditions:** Phases 4 and 7, on a grizzly-agent revision gantry pins.
- **Shape when done:** gantry calls models only through a core `Model` backed by the OpenAI-compatible provider, configured from gantry's existing endpoint and key settings, with gantry's per-role timeouts applied at the call and carried into each role's ResponseEval cases as per-case timeouts (none for observer and reflector, matching production). Its own chat types, client, retry and stream reader are deleted. Every place gantry builds or reads conversation history uses core's message model, with all of a round's tool results in one user message. Gantry's tools advertise core `ToolSpec`s; its own dispatch stays. Structured-output requests use core's response format. Role-tier evals are ResponseEval cases built from gantry's existing case files, production request builders and production parsers. The harness tier keeps its own runner and scorer and records its repeats into the shared report, so one `gantry eval` invocation yields one report. gantry's tests use core's scripted provider. gantry's decision records about its own client, streaming and retry are superseded to say these now come from grizzly-agent.
- **Verification:** gantry's full gate passes; its loop, role and eval tests pass on the scripted provider; a `gantry run` of an example spec and a `gantry eval` of the role tier both complete against the real endpoint (run by hand), with the eval report showing per-category counts; a harness-tier case runs and appears in the same report; gantry's dependency tree no longer contains its own SSE reader or retry code.

## Phase 9 — Core turn loop and `Agent`

- **Modules:** `grizzly-agent-core` (system prompt sections, limits, `Agent`, run loop, `RunRecord`, run observer).
- **Preconditions:** Phases 2 and 3.
- **Shape when done:** `Agent` built from a `Model`, a `ToolSet`, an ordered list of static and dynamic system-prompt sections, and limits (round limit default 16, stall threshold default 4); `Send + Sync`, with `run(&self, …)` safe to call concurrently. `Agent::run` takes the conversation, a `CancellationToken` and an optional per-run observer; it returns `Result<RunRecord, RunFailure>`: `RunFailure::InvalidConversation` up front for a conversation containing system messages or breaking the request invariants, `RunFailure::Provider` (with the `ProviderFailure` as `source()` and the `RunTrace` so far) when a model call fails after retries, and otherwise a `RunRecord`. It calls the model through `Model::stream` with the accumulator, forwards events to the observer, and follows the design's completion rules (max-tokens → `Truncated` with nothing dispatched and tool-use blocks stripped from the appended message; tool uses → dispatch in order and continue; otherwise → `Completed`), stop-request check, stall counting, cancellation checks before model calls and tool dispatches, a `tracing` warning per tool failure and a `tracing` error per failed run. `RunTrace` carries the appended messages, per-round records (usage, stop reason, latency, each tool call with arguments, failure flag and latency) and total usage with unknown propagation; `RunRecord` is the ending (`Completed`, `Truncated`, `StopRequested`, `RoundsExhausted`, `Stalled`, `Cancelled`), final reply and trace. `TurnFailure` no longer exists. Re-exported through the facade.
- **Verification:** an upfront `InvalidConversation` is returned for a system message in the conversation; two concurrent runs on one `Agent` with separate observers each see only their own events; a `Truncated` record's transcript, passed back to `run`, is accepted; scripted-provider tests reach every ending (`Completed`, `Truncated`, `StopRequested`, `RoundsExhausted`, `Stalled`, `Cancelled`) and assert the record's contents for each; a provider failure in a later round returns `Err(RunFailure::Provider)` whose `source()` is the `ProviderFailure` and whose trace holds the earlier rounds, and propagates through `?` into an `anyhow` error whose chain names the provider failure; the tool-failure warning and run-failure error events are emitted (captured with a test subscriber); stall counting resets on any different call and treats key-reordered arguments as identical; a failing tool becomes a tool result and the run continues; section rendering drops empty sections and joins with a blank line, and a dynamic section's change is visible on the next round; the observer sees every event, round and tool call in order; total usage is unknown when any round's is.

## Phase 10 — AgentEval

- **Modules:** `grizzly-agent-eval` (AgentEval trait and runner).
- **Preconditions:** Phases 7 and 9.
- **Shape when done:** the four-part AgentEval case trait (build a fresh `Agent`, set up the environment returning the task input, check the environment returning check results, score the `RunRecord` with the check results) and a runner that drives set up → run → check → score per repeat, maps `RunFailure::Provider` to `Unavailable` (skipping check and score, keeping the failure's trace in the detail), and `RunFailure::InvalidConversation` and set-up or check errors to `Failed`, runs one repeat at a time by default with a configurable limit, and records ending, total usage, round count and check results in the detail, plus the full transcript on a miss.
- **Verification:** tests with scripted agents over a temporary scratch directory cover a passing repeat, a scorer miss, a check that fails, a set-up error, and a provider failure, asserting category, detail contents and transcript retention on misses only; repeats are sequential by default and bounded by the limit when raised.

## Phase 11 — Skills

- **Modules:** new `grizzly-agent-skills` package (format, index, activation state, activate and deactivate tools, dynamic system-prompt section); facade feature `skills`.
- **Preconditions:** Phases 5 (frontmatter default face), 2 and 9.
- **Shape when done:** the format layer parses `SKILL.md` via prompts' frontmatter face into the six spec fields with the design's validation (including `allowed-tools` accepted as a space-delimited string or a YAML list), preserving unknown keys and enforcing no vendor-specific rules; the index scans an ordered list of directories with first-directory-wins precedence, reporting and skipping duplicates and invalid skills, and renders a name-and-description listing; activation holds shared state, provides the two tools as `ToolHandler`s, and provides a dynamic section rendering the index and active skills' bodies. `allowed-tools` is exposed and not enforced. The skills crate depends on prompts' default features only.
- **Verification:** table tests cover every validation rule and both `allowed-tools` forms; index tests cover precedence, duplicate reporting and skipping invalid skills without failing the scan; an end-to-end scripted `Agent` run activates a skill through its tool and the next round's system message contains that skill's body, then deactivates it and the body is gone; `cargo tree` shows skills pulls no codegen dependencies.

## Assembled-whole check

After Phase 11, confirm the design's intent end to end: a new scratch consumer crate, depending only on `grizzly-agent` (features `openai`, `skills`, `eval`) and `grizzly-agent-prompts` (build edge, `codegen`), defines a tool in a prompt file, runs an `Agent` with that tool and a skill against a real endpoint while printing streamed text live through the observer, and scores the same agent with one AgentEval case and one ResponseEval case — with no provider-specific code outside the `Model` construction. gameservers and gantry both build and pass their gates against the same grizzly-agent revision.
